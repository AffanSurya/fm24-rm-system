# Intelligent Player Recommendation System for Football Manager 24
## Implementation Plan

This plan is grounded in the actual export schema found in your sample files: per-player exports carry 47 numeric FM attributes spanning technical, mental, physical, and goalkeeping categories (Cor, Cro, Dec, Det, Vis, Acc, Pac, Aer, Ref, Han, 1v1, TRO, etc.), plus categorical fields (Style, Best Pos, Best Role, Best Duty, Position eligibility string, Inf status codes like "Wnt"/"Inj"/"Lst"), scouting metadata (Knowledge level, RF Matches / recruitment focus count, masked Ability/Potential that only resolve once a player is fully scouted), and financial fields (Transfer Value as a banded range, Salary as monthly wage). Squad files (arsenal_*.html, senior.html, u-21.html) and scouting/shortlist files (left_defender, right_defender, left_winger, right_winger) share this schema but differ in completeness — squad files have full attribute visibility, scouting files often have masked CA/PA and variable attribute confidence tied to Knowledge level. The architecture below treats this asymmetry as a first-class concern rather than an edge case.

## 1. Data Ingestion Pipeline Design

**Source heterogeneity.** FM24 exports arrive as HTML tables (saved views) or RTF (printed views), with column sets that vary by view configuration — your samples show 56-column squad views and 59-column scouting views, with column order not guaranteed to be stable across exports (FM lets users reorder/add/remove columns per view, and patches occasionally rename or add attributes). The ingestion layer should therefore never hardcode column position; it parses the header row of each file independently and builds a per-file column map, validated against a canonical attribute dictionary at load time.

**Parsing layer.** Two format-specific extractors (HTML table parser, RTF pipe-table parser) normalize into a common intermediate representation before anything else touches the data. This isolates the rest of the pipeline from FM's export quirks — RTF files in particular encode tables as fixed-width pipe-delimited text with separator rows, which is structurally different from HTML's tag-based table but should resolve to identical output records.

**Schema normalization.** A canonical schema maps every observed FM abbreviation (Tck, Wor, Vis, Cmp, Ant...) to a stable internal attribute key with category tagging (technical / mental / physical / goalkeeping). This matters for two reasons specific to your data: first, outfield and goalkeeping attribute sets overlap in the export (a GK row populates Han, Ref, Cmd, 1v1, TRO, Aer alongside generic mental/physical attributes, while outfield players leave those columns at low/irrelevant values), so the normalizer should tag rows by inferred player type and route GK-specific scoring logic accordingly; second, categorical fields need controlled vocabularies — Best Role and Best Duty values map to FM's fixed role taxonomy (Sweeper Keeper, Complete Wing Back, Deep Lying Playmaker, etc.), which should be validated against a maintained role registry rather than treated as free text, since typos or future-patch role renames would otherwise silently break role-matching logic downstream.

**Financial field parsing.** Transfer Value arrives as a banded range (e.g. "€6.8M–€8M") rather than a point estimate, and Salary as a periodic figure ("€5,750 p/m"). These need dedicated parsers that extract currency, magnitude multiplier, and either a point value or a (low, high, midpoint) tuple — the range itself is informative (wider bands generally correlate with lower scouting confidence or higher valuation volatility) and should be preserved as a feature, not collapsed prematurely to a single number. Salary should be normalized to a common period (annualized) for comparability against transfer fee amortization in later budget logic.

**Scouting confidence as metadata.** The Knowledge field (None/Minimal/Average/Good/Extensive/Full) and the masking of Ability/Potential are signal, not noise. A record where Ability/Potential are blank and Knowledge is "Minimal" should be flagged with a confidence tier that propagates through the feature store and ultimately tempers how aggressively the recommendation engine ranks that player — an unscouted wonderkid with sparse data shouldn't be silently treated as average. The Inf column (status codes for injury, transfer interest, contract situation, listed status) should be parsed into discrete boolean/categorical flags (is_injured, is_wanted, is_listed, is_unsettled) since these directly affect actionability of a recommendation regardless of attribute quality.

**Pipeline stages.** Raw file → format-specific parse → header-driven column mapping → canonical schema coercion (type casting, range parsing, status decoding) → row-level validation (attribute bounds 1–20, required-field checks, duplicate-name resolution within a club) → versioned write to a normalized player store, partitioned by export batch/date so that attribute drift across FM patches or save-game progression is auditable rather than silently overwritten.

**Idempotency and merge logic.** Because the same player can appear across multiple files (a squad player might also appear in a positional scouting export, or the same shortlist re-exported after a scouting update), ingestion needs an entity-resolution step — match on name + nationality + age band + club as a composite key, with conflict resolution that prefers the higher-Knowledge-confidence record per attribute rather than naively overwriting.

## 2. Feature Engineering Methodology

**Raw attribute tier.** The 47 base attributes form the lowest-level feature tier, used directly by role-suitability scoring but rarely fed raw into similarity or ranking models, since their pairwise correlations are strong (e.g. Acceleration/Pace, Decisions/Anticipation/Composure cluster together) and raw use would over-weight correlated clusters.

**Role suitability scores (the central derived feature).** FM's own Best Role/Best Duty/Ability fields are useful but reflect FM's internal weighting, not your tactical philosophy. The system should compute its own role-fit scores per (player, role, duty) combination using published-style weighted attribute formulas analogous to what FM uses internally and what the analytics community has reverse-engineered (weighted sums of the attributes relevant to each role, e.g. a Deep Lying Playmaker weighting Passing, Vision, Composure, Decisions, Technique heavily and Tackling lightly; a Complete Wing Back weighting Pace, Stamina, Crossing, Dribbling, Work Rate, Acceleration, with positional attributes like Tackling moderate). Maintain this as an explicit, versioned weight matrix (role × attribute → weight) rather than embedding it in code logic, so weights can be tuned per your playing philosophy without redeploying the pipeline. This produces a role-fit score per player per role-duty pair, independent of FM's own Ability rating — critical because Ability/Potential are frequently masked for scouted players, while raw attributes (even partially known ones) are not.

**Positional versatility encoding.** The Position eligibility string (and, where present, Best Pos) should be expanded into a multi-hot positional matrix (GK, D(L/C/R), WB(L/R), DM, M(L/C/R), AM(L/C/R), ST, etc.) rather than a single label, since FM players are frequently eligible across several positions with varying proficiency. Versatility itself becomes a derived scalar feature (count of positions at green/competent proficiency, weighted by how tactically relevant each is to your formation), which matters for squad depth and rotation analysis independent of best-fit role.

**Tactical compatibility metrics.** Given a target formation + playing style (e.g. "4-3-3 Gegenpress" vs "5-2-3 Possession"), compute a compatibility vector per player: (a) role-fit score for every role the formation's slot supports, (b) a physical/mental profile match against the style's demands (high-press styles weight Stamina/Work Rate/Aggression/Pace heavily; possession styles weight Technique/Composure/Decisions/Passing), and (c) a formation-slot coverage indicator (does this player fill one or more slots in the specific formation shape). This is what allows the engine to be queried with arbitrary formation/role/style combinations rather than a fixed set of pre-computed labels.

**Financial features.** Transfer Value midpoint and band-width, annualized salary, and an estimated value-to-attribute-output ratio (role-fit score divided by transfer value, log-scaled given the heavy right-skew of football transfer fees) form the value-efficiency feature set used in optimization (Section 4). Age is retained both as a raw feature and as an input to a simple value-trajectory adjustment, since a 19-year-old and a 31-year-old with identical current role-fit scores represent very different investments.

**Age-curve modeling.** Age shouldn't be treated as a flat adjustment factor — it needs its own derived feature tier because its effect on value differs by what's being evaluated. Three distinct age-driven signals are worth separating rather than collapsing into one "age score": (1) a current-fit trajectory, modeling whether a player's role-fit score is likely rising, plateaued, or declining given typical age-curves for their position group (technical/mental attributes for playmaking roles tend to peak later and decay slower than the pace-dependent physical attributes that wing-backs, wingers, and out-and-out pace-reliant forwards rely on, so the decline curve should be position-and-role-aware, not a single global age-vs-output function); (2) a potential-realization signal for young players, combining Age, (when unmasked) the Potential field, and role-fit trajectory to flag players who don't yet fit a target role well on current attributes but are positioned to with development time — this matters specifically for transfer recommendations where buying ahead of need is a valid strategy, and should be surfaced as a distinct "developing fit" category rather than mixed into current-fit ranking; (3) a value-trajectory signal pairing age against the Transfer Value band, since value bands compress and shift downward as players age past their peak, independent of whether current attributes have declined yet — this is what lets retention scoring distinguish "ageing player still performing, sell now while value holds" from "ageing player still performing, value is stable, fine to keep." Each of these three signals should remain a separate feature rather than being pre-merged, since squad optimization, transfer recommendation, and retention scoring each weight them differently (squad optimization cares most about current-fit trajectory and depth continuity; transfer recommendation cares most about potential-realization for younger targets and decline risk for older ones; retention scoring cares most about value-trajectory).

**Confidence-weighted features.** Every derived score should carry a parallel confidence weight derived from Knowledge level and band-width of Transfer Value, so downstream ranking can either discount uncertain players or surface them in a separate "high potential, low confidence" bucket rather than silently mis-ranking them against fully-scouted players.

**Normalization.** Z-score or percentile normalization should be computed within relevant comparison populations (e.g. percentile rank among players eligible for the same role, not the entire dataset), since raw attribute scales are flat (1–20) but role-relevance varies — comparing a striker's Tackling percentile against the global player pool is meaningless, but comparing his Finishing percentile against other strikers is the actual signal.

## 3. Recommendation Model Architecture

**Why content-based, not collaborative filtering.** Collaborative filtering depends on dense interaction signals across many users (who "selected" which players in what context) to find latent similarity structure. This domain has neither — there's a single decision-maker (you, with one evolving tactical philosophy) and no meaningful interaction matrix; sparsity isn't a CF tuning problem here, it's a structural mismatch, since CF would have nothing to collaborate against. A pure content-based approach, where players are represented by the engineered feature vectors above and ranked against an explicit tactical query, is the correct fit: it's interpretable (you can trace why a player ranked highly back to specific attribute contributions), works with a single example formation/role specification rather than needing historical "preference" data, and generalizes immediately to new formations or roles without retraining, since role-fit is computed analytically from the weight matrix rather than learned from past selections.

**Where a learned layer adds value.** A pure weighted-sum content model is transparent but can't easily capture nonlinear interactions (e.g. diminishing returns of Pace without Acceleration, or role-specific attribute synergies that aren't well captured by independent linear weights) or absorb feedback over time (you mark a recommendation as good/bad and the system should adjust). The recommended architecture is therefore a hybrid: a deterministic, explainable content-based scorer as the primary ranking mechanism (auditable, role-weight-driven, requires no training data to function from day one), with an optional learned re-ranking layer — a gradient-boosted tree (LightGBM/XGBoost-style) trained on your accumulated feedback (squad decisions you confirm, transfers you actually execute, sell decisions you act on) that adjusts the base content score using interaction features and historical decision patterns. This learned layer is additive and falls back gracefully to pure content-based scoring when feedback volume is too low to train reliably (a cold-start guard, e.g. a minimum labeled-decision threshold before the re-ranker activates) — appropriate given a single-user, low-volume-feedback setting where a fully learned model would overfit immediately.

**Player-to-player similarity (auxiliary use case).** For "find a replacement for player X" or squad-depth analysis, a separate embedding space (PCA or autoencoder-reduced attribute space, role-aware) supports nearest-neighbor similarity search independent of the role-fit scorer — useful for sell-decision support ("if I sell this player, who in the data already resembles his profile") without conflating it with the primary recommendation ranking logic.

**Three-mode design.** All three use cases (squad optimization, transfer recommendation, retention/sale) route through the same underlying scorer with different input framing and output framing: squad optimization queries the scorer against the current 23-25 man squad and a target formation/style, surfacing fit scores per current player; transfer recommendation queries the scorer against an external candidate pool (your scouting export files) filtered by target position/role; retention/sale inverts the framing, combining role-fit score with replaceability (similarity-search density — how many comparable or better alternatives exist at acceptable value) and financial opportunity cost (Section 4) to produce a keep/sell signal rather than a pure fit ranking.

## 4. Multi-Objective Optimization Framework

Buy/sell/keep decisions are not single-objective ranking problems — role-fit and financial efficiency frequently conflict, and a pure performance-maximizing recommendation ignoring cost is not useful to you given the explicit valuation constraint.

**Objectives.** (a) on-pitch fit — the role-fit/tactical-compatibility score from Section 2; (b) value efficiency — fit-per-cost, where cost for buy decisions is transfer value (amortized over expected useful years remaining, derived from the age-curve trajectory in Section 2 rather than a flat fee) and for retention decisions is opportunity cost (sale value forgone vs. wage saved vs. fit lost); (c) age-adjusted return — a distinct objective from raw value efficiency, weighing remaining-years-at-current-or-improving-fit against cost, so a younger player at a slightly lower current fit but rising trajectory can outrank an older player with a marginally higher current score but a flatter or declining one, particularly for transfer decisions where the investment horizon matters as much as today's snapshot; (d) budget feasibility — hard constraint against available transfer budget and wage structure ceiling, not a soft-weighted objective, since exceeding budget isn't a worse recommendation, it's an invalid one; (e) squad balance — positional depth coverage, age-curve distribution across the squad (avoiding a cluster of players all aging out of peak fit in the same 2–3 year window), and avoiding over-concentration of a single role/duty.

**Framework choice.** Rather than collapsing everything into one scalar score (which hides trade-offs and requires arbitrary weight tuning that's hard to justify to yourself later), the recommended approach is constrained multi-objective ranking: budget and wage-structure constraints are hard filters applied first (infeasible candidates are excluded or flagged separately, never silently ranked alongside feasible ones); among feasible candidates, fit, value-efficiency, and age-adjusted return are surfaced as a Pareto frontier rather than a single merged score, so the output is structured as "best fit regardless of cost," "best value efficiency," "best long-term investment," and "best balanced," letting you apply your own judgment on the trade-off per decision rather than the system imposing one. A single blended score is offered as a convenience default (configurable weighting between fit, value-efficiency, and age-adjusted return) but the Pareto view should always be available underneath it for transparency.

**Sell-side logic.** For retention scoring, the optimization explicitly weighs current role-fit and squad necessity against the value-trajectory signal from Section 2 and wage burden — a player who is a strong tactical fit but on a depressed valuation trajectory (age-driven decline approaching, value band widening downward) surfaces differently than one with stable or rising value, since the "must keep" vs "sell now while value holds" distinction depends on age-driven trajectory, not just current fit. This is also where the potential-realization signal cuts the other way: a young, currently-modest-fit player with a strong developing-fit trajectory should rarely surface as a sell candidate purely on today's role-fit score, even if an older squad-mate currently outscores them.

**Squad balance as a soft constraint.** Depth coverage is modeled as a penalty/bonus term rather than a hard constraint, since recommending a transfer that creates short-term excess at one position to acquire a clearly superior long-term option is sometimes correct — squad balance should inform ranking, not block it outright the way budget does.

## 5. API / Service Design

A clean separation between three primary capabilities, all backed by the same scoring core, with explicit support for the tactical-constraint-as-input requirement:

- **Squad analysis endpoint** — accepts a current squad identifier (or file reference), target formation, playing style, and an explicit role assignment or "auto-assign optimal roles" flag; returns per-player fit scores against their assigned (or best-fit) role, a must-keep/contested/sell-candidate classification, and squad-balance diagnostics (depth gaps, age-curve summary, role redundancy).
- **Transfer recommendation endpoint** — accepts target position(s), target role(s)/duty, formation and style context, a candidate pool reference (one or more scouting export files), and budget/wage constraints; returns ranked buy candidates with fit score, value-efficiency score, feasibility flag, and confidence tier (surfacing the Knowledge-level caveat explicitly rather than hiding it), with the Pareto-frontier view available as a query parameter.
- **Retention/sale scoring endpoint** — accepts a player or full-squad reference and the same tactical context; returns a keep/sell recommendation with the contributing factors broken out (fit, replaceability, value trajectory, wage burden) rather than a single opaque score, since sell decisions carry real consequences and deserve explainability.
- **Supporting endpoints** — ingestion/upload endpoint accepting new export files and triggering the normalization pipeline; a role-weight configuration endpoint allowing you to view and adjust the role × attribute weight matrix (so the "playing philosophy" input is itself editable rather than fixed); a feedback endpoint for confirming/rejecting recommendations, which is what feeds the optional learned re-ranking layer in Section 3.

All scoring endpoints should accept the tactical constraints (formation, style, role, duty) as structured query parameters validated against the role/formation registry, not free text, so invalid combinations (a role that doesn't exist in the requested formation slot) fail fast with a clear error rather than silently producing a meaningless score.

## 6. Evaluation Methodology

Validating recommendation quality here is harder than in typical recsys settings because there's no large historical interaction log to hold out. The practical approach combines three validation strategies:

**Internal consistency checks against FM's own ratings.** FM exposes Best Role/Best Duty and (when unmasked) CA/PA as a baseline. The content-based scorer's role-fit rankings should correlate strongly with FM's own Best Role assignment for well-scouted players as a sanity check — large systematic divergence signals a weighting-matrix error rather than genuine insight, since the role-fit formula is intentionally modeled on the same attribute-weighting logic FM uses internally. This isn't the target to optimize toward (your custom playing-style weighting is supposed to differ from FM's generic Best Role in tactically meaningful ways) but it's the right tool for catching implementation bugs.

**Backtesting against known outcomes within your save.** Because this is a single-save, single-decision-maker system, the most meaningful evaluation is retrospective: take a squad/transfer-window snapshot from N months prior (if available from earlier export batches), generate recommendations as they would have been made at that point, and compare against what actually happened in-game since (did "must keep" players perform well in actual match outcomes if match data is exportable; did "sell candidates" decline in value or game time as predicted; did recommended transfer targets, if signed, deliver fit-consistent output). This requires no external benchmark and directly tests calibration against your specific save's dynamics.

**External football-analytics grounding for the weight matrix itself**, independent of FM. The role-attribute weightings should be cross-checked against published football-analytics role definitions and known archetypal player comparisons (e.g. does the Deep Lying Playmaker weighting correctly rank attribute profiles resembling publicly known DLP archetypes higher than ones resembling a Box-to-Box Midfielder) — this validates that the weight matrix encodes real tactical logic rather than FM-specific quirks, and gives you a defensible basis for the weights beyond "FM says so."

**Offline ranking metrics once feedback accumulates.** Once the feedback endpoint has enough labeled decisions (confirmed/rejected recommendations), standard ranking evaluation (NDCG or precision@k against your accept/reject labels) becomes available to validate the optional learned re-ranker specifically, separate from the base content-based scorer.

## 7. Deployment Considerations for Iterative Updates

**Patch-driven attribute drift.** FM patches periodically rebalance attribute distributions, add/rename attributes, or alter role definitions (new roles, retired roles, duty changes). The schema normalization layer (Section 1) and the role-weight matrix (Section 2) should both be versioned artifacts with explicit compatibility metadata (which FM version/patch they were built against), not silently mutated in place. On detecting a new patch's export (new/missing columns relative to the canonical schema, or unrecognized role values), the ingestion pipeline should flag the mismatch for review rather than silently dropping or misattributing columns.

**Re-baselining normalization statistics.** Percentile-based normalization (Section 2) is population-relative, so if your save's available player pool shifts meaningfully (new scouting region unlocked, several transfer windows passed), normalization baselines should be recomputed periodically rather than frozen at first-ingestion statistics, or fit-score comparisons across time will silently drift in meaning.

**Weight matrix as a living config, not a retrained model.** Because the core scorer is content-based and weight-matrix-driven rather than trained end-to-end, "updating the model" after a patch is primarily a configuration review (does this role's attribute weighting still reflect its in-game effectiveness) rather than a retraining job — this is a deliberate architectural advantage of the hybrid design in Section 3 over a fully learned approach, which would otherwise need retraining data after every meaningful patch.

**Feedback-layer staleness.** If the optional learned re-ranker (Section 3) is active, a patch that meaningfully shifts attribute distributions should trigger a confidence downgrade or temporary deactivation of that layer until enough post-patch feedback accumulates, since it was trained on pre-patch decision patterns that may no longer hold.

**Versioned player store.** Carrying forward the partitioned/versioned ingestion design from Section 1, each normalized export batch should be retained (not overwritten) specifically so that the backtesting evaluation strategy in Section 6 remains possible over time — deployment and evaluation are coupled here in a way that's easy to overlook if the player store is treated as a simple upsert table.
